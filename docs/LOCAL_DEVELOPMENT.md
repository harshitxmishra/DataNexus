# DataNexus — Local Development & Setup Guide

This guide provides exact, tested step-by-step instructions for running, testing, and developing DataNexus locally on Windows, macOS, or Linux.

---

## 1. Prerequisites

- **Python**: 3.11, 3.12, or 3.13 (64-bit)
- **Node.js**: v18.0.0 or higher
- **npm**: v9.0.0 or higher
- **Git**: 2.30+

> **Note on Docker**: Docker is **not** required for local development. DataNexus is architected to run out of the box using native Python virtual environments and an embedded SQLite database with zero external service dependencies.

---

## 2. Quickstart (Under 3 Minutes)

### Step 1: Clone and Configure Environment
```bash
git clone https://github.com/harshitxmishra/DataNexus.git
cd DataNexus
cp .env.example .env
```

### Step 2: Set Up Backend Virtual Environment
**Windows PowerShell**:
```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r backend/requirements.txt
```

**macOS / Linux**:
```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r backend/requirements.txt
```

### Step 3: Set Up Frontend Dependencies
```bash
cd frontend
npm install
cd ..
```

### Step 4: Seed Demonstration Data
Run the database seeder to generate 6 sample PDF invoices and initial dimensional star-schema facts:
```bash
python scripts/seed_database.py
```

### Step 5: Start Development Servers

**Terminal 1 — Backend (FastAPI)**:
```bash
# From project root:
.venv\Scripts\uvicorn backend.app.main:app --host 127.0.0.1 --port 8008 --reload
# (On macOS/Linux: uvicorn backend.app.main:app --host 127.0.0.1 --port 8008 --reload)
```
*API Swagger Documentation is available at: `http://127.0.0.1:8008/docs`*

**Terminal 2 — Frontend (Vite + React)**:
```bash
cd frontend
npm run dev
```
*Frontend Application opens at: `http://localhost:5173` (or `http://localhost:5174` if port 5173 is in use).*

## 4. Database Configuration & Migrations

DataNexus features dual-mode database support:
- **SQLite**: Default zero-dependency local development (`sqlite:///./datanexus.db`).
- **PostgreSQL**: Production-grade operational & analytical database (`postgresql+psycopg2://...`).

### 4.1 Running Alembic Migrations
Alembic manages all schema lifecycle migrations:
```bash
# Apply all pending migrations:
alembic upgrade head

# Generate offline PostgreSQL DDL without connecting to a live cluster:
alembic upgrade head --sql

# Create a new autogenerated schema migration revision:
alembic revision --autogenerate -m "describe_changes"
```

### 4.2 Connecting to PostgreSQL
1. Start PostgreSQL (e.g., via Docker or native service):
   ```bash
   docker run -p 5432:5432 -e POSTGRES_DB=datanexus -e POSTGRES_PASSWORD=postgres -d postgres:16
   ```
2. Update `.env`:
   ```env
   DATABASE_URL=postgresql://postgres:postgres@localhost:5432/datanexus
   ```
3. Run Alembic migrations to initialize all tables:
   ```bash
   alembic upgrade head
   ```

### 4.3 Migrating Data from SQLite to PostgreSQL
DataNexus includes a zero-data-loss migration utility that copies all existing documents, chunks, extracted fields, stage events, dimensional star schema facts, data quality scores, and lineage graphs from SQLite into PostgreSQL:
```bash
python scripts/migrate_sqlite_to_postgres.py --target-url postgresql://postgres:postgres@localhost:5432/datanexus
```

## 5. Elasticsearch Configuration & Search Integration

DataNexus supports full-text BM25 search, dense vector k-NN retrieval, and hybrid Reciprocal Rank Fusion (RRF) using an external Elasticsearch cluster (version 8.x or 9.x), with an automatic, zero-dependency in-process local search fallback when Elasticsearch is offline.

### 5.1 Environment Variables
Configure Elasticsearch in `.env`:
```env
# Elasticsearch Cluster Endpoint
ELASTICSEARCH_URL=http://localhost:9200

# Authentication (optional)
ELASTICSEARCH_USERNAME=elastic
ELASTICSEARCH_PASSWORD=changeme

# Index Configuration & Connection Tuning
ELASTICSEARCH_INDEX=datanexus_chunks
ELASTICSEARCH_TIMEOUT_SECONDS=3.0
ELASTICSEARCH_MAX_RETRIES=2
ELASTICSEARCH_RETRY_ON_TIMEOUT=true
ELASTICSEARCH_VERIFY_CERTS=true
ELASTICSEARCH_CA_CERTS=""
```

### 5.2 Starting a Local Elasticsearch Instance
If Docker is available:
```bash
docker run -d --name datanexus-es \
  -p 9200:9200 \
  -e "discovery.type=single-node" \
  -e "xpack.security.enabled=false" \
  docker.elastic.co/elasticsearch/elasticsearch:8.15.0
```

### 5.3 Index Lifecycle, Reconciliation & Reindexing
PostgreSQL (or SQLite) is the canonical source of truth for all document chunks. When Elasticsearch is online, chunks are indexed idempotently during document processing. If Elasticsearch is offline or suffers a transient failure, chunks are marked unindexed (`indexed_in_es = False`) and tracked in the outbox.

To check search engine status and index alignment via the REST API:
```bash
# Check status and unindexed outbox count:
curl http://127.0.0.1:8008/api/search/status

# Run index reconciliation to compare database chunks with Elasticsearch:
curl -X POST http://127.0.0.1:8008/api/search/reconcile

# Reindex all document chunks from the canonical database into Elasticsearch:
curl -X POST http://127.0.0.1:8008/api/search/reindex
```

## 6. Pretrained Neural Embeddings & Re-Embedding Workflow

DataNexus uses `sentence-transformers/all-MiniLM-L6-v2` as its canonical pretrained embedding model, generating 384-dimensional unit-$L_2$-normalized dense vectors for chunk indexing and semantic search.

### 6.1 Configuration Options
In `.env`:
```env
EMBEDDING_PROVIDER=sentence_transformers
EMBEDDING_MODEL_NAME=sentence-transformers/all-MiniLM-L6-v2
EMBEDDING_MODEL_REVISION=1110a243fdf4706b3f48f1d95db1a4f5529b4d41
EMBEDDING_REPRESENTATION_VERSION=2
EMBEDDING_DEVICE=cpu
EMBEDDING_BATCH_SIZE=32
```

### 6.2 Idempotent Re-Embedding
When migrating from legacy representations (Version 1) to neural representations (Version 2), or after updating models:
```bash
# Re-embed all eligible chunks (skipping chunks already at version 2):
curl -X POST http://127.0.0.1:8008/api/search/reembed

# Force re-embedding of all chunks even if already at version 2:
curl -X POST "http://127.0.0.1:8008/api/search/reembed?overwrite=true&batch_size=32"
```

### 6.3 Running the Retrieval Benchmark
Execute the formal 10-query retrieval evaluation suite comparing BM25, Interim Hashing, Pretrained MiniLM, and Hybrid RRF:
```bash
python -m backend.app.evaluation.retrieval_eval
```

## 7. GroqCloud LLM Integration & Grounded Question Answering (Phase 4)

DataNexus incorporates high-speed GroqCloud LLM inference for grounded Question Answering / RAG with negative question gating and verifiable citations.

### 7.1 Configuration Options
Configure GroqCloud credentials and inference settings in `.env`:
```env
# LLM Provider Configuration
LLM_PROVIDER=groq
GROQ_API_KEY=gsk_your_groq_api_key_here
GROQ_MODEL=qwen/qwen3.8-27b
GROQ_FALLBACK_MODELS=llama-3.3-70b-versatile,llama-3.1-8b-instant,openai/gpt-oss-120b,openai/gpt-oss-20b
GROQ_TEMPERATURE=0.1
GROQ_MAX_TOKENS=800
GROQ_TIMEOUT_SECONDS=15.0
```

> **Note**: If `GROQ_API_KEY` is omitted or unset, DataNexus automatically falls back to deterministic local extractive synthesis without service degradation or errors.

### 7.2 Testing Question Answering via cURL / HTTP
Execute a grounded QA query against the active backend server:
```bash
# Query with sufficient evidence in seeded invoices:
curl -X POST http://127.0.0.1:8008/api/search/qa \
  -H "Content-Type: application/json" \
  -d "{\"question\": \"What is the total amount due for invoice INV-2024-001?\"}"

# Query with negative/insufficient evidence:
curl -X POST http://127.0.0.1:8008/api/search/qa \
  -H "Content-Type: application/json" \
  -d "{\"question\": \"What is the company vacation and sick leave policy?\"}"
```

### 7.3 Checking LLM Readiness Probe
Verify LLM provider status via the readiness endpoint:

## 10. Troubleshooting Common Issues

### Issue 1: Port 8000 or 8008 Already in Use
- **Cause**: Another local process is bound to the target port.
- **Solution**: Pass an alternative port to Uvicorn (e.g. `--port 8009`) and update `target` in `frontend/vite.config.ts`.

### Issue 2: Python ModuleNotFoundError When Running Pytest
- **Cause**: Running `pytest` instead of `python -m pytest` might omit the current working directory from `sys.path`.
- **Solution**: Always invoke as `.venv\Scripts\python -m pytest backend/tests -v`.

### Issue 3: SQLite Database Locked
- **Cause**: Multiple write transactions concurrent with external SQLite database viewers.
- **Solution**: Close external database GUI tools (e.g., DB Browser for SQLite) when running write-heavy batch ETL scripts.

### Issue 4: Cold-Start Latency for Embedding Model
- **Cause**: Initial cold load of PyTorch runtime and Transformer weights into memory on CPU takes 10-15 seconds.
- **Solution**: The model remains memory-resident across requests within the process lifecycle; subsequent inferences run in 25-30ms per batch.
